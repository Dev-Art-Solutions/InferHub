# The Python for the :diffusion image (phase 46). Nothing here is a .csproj dependency — design
# rule 5 is intact and `InferHub.Shared.csproj` is still empty. The node speaks a *process* protocol
# and does not know what language a worker is in (phase-41 D1); this file is what the image happens
# to install so that the diffusion worker has its libraries.
#
# SEPARATE FROM requirements-tools.txt, on purpose. The `:tools` image (Whisper + Piper) is 5.6 GB
# and the torch CUDA wheels are several gigabytes more; stacking them would put PyTorch into every
# audio deployment and Whisper into every image one. The `:diffusion` image carries this file and
# nothing from the other, which is phase-46 D9 stated in a requirements list — see Dockerfile.diffusion.
#
# PINNED, for phase-39 D9's reason: two builds of the same InferHub tag containing different
# inference engines makes "it worked in 3.14.0" a question nobody can answer. Bump deliberately,
# rebuild, and re-run the published-image checks — not because a resolver picked something newer
# overnight.
#
# PINNED BY VERSION, NOT BY HASH, and that is the same deliberate step down phase 42 took: a hash
# set that is subtly wrong does not fail loudly, it fails the image build with something that reads
# like a network error, after which the next person deletes the hashes. Version pins answer the
# question D9 was protecting, and the published image's own digest is the byte-level anchor. If this
# ever moves to hashes, generate them in CI against the image, never by hand.
#
# bitsandbytes ARRIVED IN PHASE 48, WITH ITS FIRST CONSUMER, and that is the whole reason phase 46
# deliberately did not carry it: a pinned dependency nothing imports is a pin nobody can tell is
# wrong until the release that needs it. FLUX.1-schnell (12B) and Qwen-Image (20B + an 8.3B text
# encoder) do not fit a 24 GB card at bf16, and nf4 is what makes them one-card models.
#
# Installing these outside the image is supported and is how you get images on the plain node:
#
#   python -m venv /opt/inferhub/venv
#   /opt/inferhub/venv/bin/pip install -r requirements-diffusion.txt
#
# The CUDA wheels are what pip resolves by default from PyPI for linux/amd64: torch bundles its own
# CUDA runtime and reaches the *driver* the container runtime injects — the same split phase-39 D1
# relies on, which is why there is no CUDA toolkit in this list and none in the image.

# ONLY THE DIRECT DEPENDENCIES ARE PINNED. The transitive closure is left to pip, for the reason
# written at the top of requirements-tools.txt: a hand-written transitive pin is a pin somebody
# guessed, and one that only CI can check is worse than no pin at all.

# The pipelines. `diffusers` is the whole client surface this worker uses; `transformers` is what
# loads the text encoders (CLIP for both recipes here), and `accelerate` is what `from_pretrained`
# wants for device placement.
diffusers==0.36.0
transformers==4.57.1
accelerate==1.11.0
safetensors==0.6.2

# The engine. Pinned to a CUDA build; the same wheel runs on a CPU and says so on its first line
# (phase-39 D6), which is the whole reason that log line exists.
torch==2.9.1

# PIL is what actually writes the PNG. diffusers pulls it in anyway; it is named here because this
# worker calls `Image.save` directly and an unnamed dependency you call directly is one that
# disappears the day the library that carried it stops needing it.
pillow==11.3.0

# Quantization (phase 48). `diffusers` drives this through `PipelineQuantizationConfig`; the recipe
# says nf4 or int8 and the worker applies it to the components the recipe names — for Qwen-Image
# that is the text encoder as well as the transformer, because an 8.3B encoder left at bf16 is the
# difference between fitting on a 24 GB card and not.
bitsandbytes==0.48.1

# FLUX's second text encoder is T5, and SD 3.5's third one is T5-XXL. `transformers` loads their
# tokenizers through `sentencepiece`, which it does NOT pull in itself, and `protobuf` is what the
# slow-tokenizer conversion path needs. CHECKED RATHER THAN ASSUMED, because a missing tokenizer
# dependency fails at first load and not at build — the v3.10.0 class of bug, where the image looks
# perfect until somebody makes a request.
sentencepiece==0.2.1
protobuf==6.33.1

# THE ENCODER (phase 57). `diffusers.utils.export_to_video` needs `imageio` with an ffmpeg backend;
# WITHOUT IT IT DOES NOT FAIL — it warns and silently drops to an OpenCV `mp4v` writer, producing a
# container nobody chose from a code path nobody read, on a job that already cost minutes of card.
# So both are pinned and the image ASSERTS the import at build time, exactly as it asserts torch.
#
# `imageio-ffmpeg` vendors a STATIC ffmpeg binary inside the wheel, which is why there is no
# `apt-get install ffmpeg` beside it: "which encoder was in 3.25.0" then has a version for an answer
# rather than whatever the distribution mirror held that week (phase-39 D9's question again).
imageio==2.37.0
imageio-ffmpeg==0.6.0

# TWO DEPENDENCIES `diffusers` USES AND DOES NOT DECLARE. Both were found on the phase-60
# verification day, on the published v3.27.0 image, and both fail at REQUEST time rather than at
# import time — which is why three releases shipped without either of them being noticed.
#
# `ftfy`: WanPipeline's `prompt_clean` calls `ftfy.fix_text(text)` UNCONDITIONALLY while the import
# above it sits behind `if is_ftfy_available():`. Without the package every single video request
# dies with `NameError: name 'ftfy' is not defined` after the model has loaded — minutes of card,
# spent, for an error that names a library nobody asked for.
#
# `peft`: `load_lora_weights` is the PEFT backend, so `qwen-360` — a rank-128 LoRA over Qwen-Image
# (phase 49) — cannot load at all without it: `ValueError: PEFT backend is required for this
# method`, raised during the background prove, so the recipe simply never becomes offerable and the
# node says nothing louder than "fetching".
#
# Both are asserted at build time in Dockerfile.diffusion, beside torch and the encoder, for the
# same reason those are: an import that only fails on somebody's first real request is the v3.10.0
# class of bug this image has now shipped three times.
ftfy==6.3.1
peft==0.17.1
