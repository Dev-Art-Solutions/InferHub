# InferHub v3.2.0 — hybrid search that runs inside Qdrant

In v3.1 keyword search on Qdrant was deliberately coarse: Qdrant's full-text index is a filter, not a
ranking, so hybrid retrieval fused a real vector branch with a rough keyword branch on the hub and
said as much in its logs. This release fixes that properly. Under `qdrant`, a `hybrid` query is now
**one Query API round trip** that fuses a dense embedding and a sparse (lexical) vector by reciprocal
rank fusion **inside Qdrant** — ranking by meaning and by exact terms at once, in the engine, instead
of the hub stitching two searches together.

Nothing changes for a deployment that sends no headers: retrieval mode still defaults to `vector`, so
results are byte-identical to v3.1.

## The sparse vector is hub-computed, and it cost no dependency

The sparse vector is the lexical view of a chunk — which terms it contains and how much each matters.
[`SparseVector`](../src/InferHub.Coordinator/Vector/Qdrant/SparseVector.cs) builds it from the **same
tokenizer the local BM25 keyword index uses** (`InvertedIndex.Tokenize`), so "the lexical view of this
chunk" means the same thing whether you run the file-backed store or Qdrant. Term indices are a stable
FNV-1a hash of each token; values are raw term frequencies.

The inverse-document-frequency weighting — the part that needs corpus statistics — is left to **Qdrant,
server-side**: hybrid collections declare their sparse vector with `modifier: idf`, so Qdrant computes
IDF from its own corpus at query time. No sparse-embedding model, no corpus statistics threaded through
the hub, no new package. Three vector backends and now server-side hybrid on one of them, and the
dependency count still has not moved since 2.3.

## How it's wired — a capability, not a widened interface

Only Qdrant can fuse server-side, so the seam grows a **capability interface**,
[`IServerSideHybridSearch`](../src/InferHub.Coordinator/Vector/IServerSideHybridSearch.cs), that only
`QdrantVectorStore` implements — the same "one implementation behind a seam" shape as `IReranker`.
`RetrievalPipeline` prefers it when the store advertises it *and* the collection is hybrid-capable, and
**falls back to hub RRF** otherwise (`local`, `postgres`, or a dense-only 3.1 Qdrant collection). It is
deliberately **not** a method on `IVectorStore`: the seam already carries three engines, and the other
two must not grow a method they would have to fake. `keyword` mode needed no pipeline fork — the
store's `SearchKeywordAsync` is a real sparse-vector search on a hybrid-capable collection and the
coarse phase-33 scroll on a dense-only one.

## Compatibility: 3.1 collections stay dense-only

A collection created on 3.2+ is a **named-vector** collection: a named dense vector plus a named sparse
vector. A collection created on 3.1 has a single unnamed dense vector and no sparse vector — it **keeps
answering vector queries** after you upgrade, and its keyword search stays coarse until it is
re-created or migrated (the cross-provider migration tool lands in v3.3). Every points/search/retrieve
call branches on the collection's shape, read back from Qdrant, so both live side by side on one Qdrant
instance.

## Verified against a live Qdrant

The gated suite was run against a real **Qdrant 1.12.4** (`INFERHUB_TEST_QDRANT` set): **40 Qdrant
tests green, 0 skipped**, including the three new phase-34 arms —

- a sparse-vector keyword search recovers an exact identifier (`E-4021`) that pure dense search misses;
- the server-side fused query recovers the exact-term chunk *and* keeps the semantically-near one;
- a dense-only (3.1-shaped) collection, created through the low-level client, still answers vector
  queries through the store and reports `SupportsServerSideHybridAsync == false`.

## Hybrid parity is a property, not a number

Different fusion engines do not produce bit-identical hybrid rankings, so the parity here is the
*property* that matters, asserted on every provider: the exact-term query that pure dense search misses
is recovered under hybrid. It holds for `local` (`RetrievalPipelineTests`) and for `qdrant`
(`QdrantVectorStoreTests`). Consistent with v3.1, the Qdrant arm lives in `QdrantVectorStoreTests`
(gated on `INFERHUB_TEST_QDRANT`) rather than the Postgres-gated `VectorProviderParityTests`.

## Eval numbers

The eval harness ([`tools/InferHub.Eval`](../tools/InferHub.Eval)) runs unchanged against a `qdrant`
coordinator — it drives `POST /api/collections/{c}/search` in every mode over HTTP and cares nothing
about the provider. Recall@k / MRR / nDCG@k for a given corpus depend on that corpus and an embedding
fleet; run it against your own golden set (its README carries the standing warning that a golden set
generated by the model under evaluation is a mirror, not evidence). No fleet was stood up for this
release, so no corpus-specific numbers are baked into a claim here.

## Tests

658 passed / 26 skipped with the Qdrant gate open (the 26 are Postgres-gated); 644 passed / 38 skipped
with both gates closed. New or extended coverage:

- `SparseVectorTests` (no server) — determinism, tokenization parity with the local keyword path
  (indices/frequencies match `InvertedIndex.Tokenize`), casing folded identically, empty/termless text
  → no vector.
- `QdrantClientTests` (no server) — the exact JSON for the hybrid create (named dense + `modifier:idf`
  sparse), the fused Query API body (dense + sparse prefetch, `fusion:rrf`, read from `result.points`),
  and the sparse-only query.
- `QdrantVectorStoreTests` (gated) — sparse keyword recovery, server-side fusion, and the dense-only
  3.1-collection compatibility path.
- `RetrievalPipelineTests` (no server) — the pipeline prefers server-side fusion when the store
  advertises it, and falls back to hub RRF when the collection is dense-only, pinned with a decorator
  store that crosses no wire.

## Zero new dependencies

Rule 5 holds again: the sparse vector is hub-computed over `System.Text.Json`, and the Query API is
more hand-rolled REST on the existing `QdrantClient`. A clean `git diff` on every `.csproj`.
